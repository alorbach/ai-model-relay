# Plan 11 — Cursor Agent image generation

**Wave:** 5 (backlog)<br>
**Depends on:** [08-cli-models-and-vision.md](08-cli-models-and-vision.md), [05-chat-isolation-and-imagine.md](05-chat-isolation-and-imagine.md)<br>

## Goal

Add Gateway **images** support for the `cursor-cli` driver via Cursor Agent’s native `GenerateImage` tool. Expose `model-relay:cursor-cli:image`, return one PNG/JPEG/WebP artifact in the normalized `{ data: [{ b64_json, mime_type }] }` shape, and keep Gateway **chat** on read-only `--mode=ask`.

## Why

Today `createCursorCliDriver` only advertises `job_types: ['chat']`. Codex, Antigravity, Grok Imagine, and xAI already cover image jobs, but operators who standardize on Cursor Agent have no Relay path for local image generation. Cursor 2.4+ ships a built-in Agent image tool; the Relay should use it the same way Antigravity uses `generate_image` — isolated temp workspace, explicit prompt contract, validated artifact import — without turning Gateway chat into a write/shell agent.

## Cursor GenerateImage — what the provider actually offers

This section is reference material for implementers. Cursor’s public docs describe the feature at a high level; the table below combines documented tool parameters with behavior measured on `cursor-agent` **2026.08.31-4057e58**. Observed dimensions and formats are compatibility observations, not readiness or output guarantees.

### Tool parameters (Agent / ACP)

| Parameter | Required | Values / notes |
|-----------|----------|----------------|
| `description` | Yes | Text prompt: subject, style, colors, layout, in-image text |
| `filePath` | No | ACP-only suggested output path; do not assume `--print` accepts it until the CLI contract is probed |
| `referenceImagePaths` | No | ACP-only absolute paths to style/composition references; do not assume `--print` accepts the field until probed |
| `aspect_ratio` | No | Not a documented ACP request field; use only as bounded prompt guidance/metadata unless a future CLI contract proves native support |
| `filename` | No | Not a documented ACP request field; do not depend on it for output naming |

There is **no documented** exposed knob for pixel dimensions, quality/compression, DPI, or 2K/4K tiers. Putting sizes in the text prompt (e.g. “512×512”) does not guarantee output dimensions. The implementation must treat the selected `--print` contract as authoritative and must not invent JSON fields or flags from the table above.

The documented ACP schema ([`cursor/generate_image`](https://prod.cursor.com/docs/cli/acp)) contains `description`, optional `filePath`, and optional `referenceImagePaths`. ACP delivers this as a fire-and-forget notification, not a request that the client can await for a normal JSON-RPC result. The docs show a separate outcome interface with optional `imageData`, but do not define a wire message carrying that outcome. Plan 11 therefore accepts only the notification’s verified `filePath` plus the generated workspace artifact; ACP reference-bearing jobs are explicitly rejected before spawn because the documented client request flow does not define how Relay-created reference paths are supplied to this notification. A future captured request contract may enable them in a separate plan. An inline `imageData` field or undocumented outcome message is rejected as `cursor_cli_unsupported` until a future plan records a real captured wire contract. It does not document `aspect_ratio` or `filename`. The Relay’s `--print --output-format stream-json` path does not use ACP today; use ACP as the verified protocol when print mode cannot provide the required tool isolation or its native event cannot be parsed reliably.

### Observed output sizes (fixed buckets)

| Requested `aspect_ratio` | Typical pixels | Megapixels |
|--------------------------|----------------|------------|
| *(default / omitted)* | 1536 × 1024 | ~1.57 (3:2 landscape) |
| `16:9` | 1536 × 1024 | ~1.57 (not true 16:9) |
| `4:3` | 1536 × 1024 | ~1.57 (not true 4:3) |
| `1:1` | 1024 × 1024 | ~1.05 |
| `9:16` | 1024 × 1536 | ~1.57 |
| `3:4` | 1024 × 1536 | ~1.57 |

Format is **PNG**, 24-bit RGB. File size is typically **~800 KB – 1.2 MB**. Some Cursor builds still default to **1376 × 768** when aspect handling is broken upstream; the Relay must accept any of these sizes after validation, not assume one resolution.

### Default save location

Generated files land under **`{workspace}/assets/`** (Cursor docs + local observation). The Relay should set `--workspace` to the per-job artifact workspace (not the separate process-temp root) so artifacts stay inside the job sandbox and disappear with workspace cleanup.

### Execution mode constraint

| Mode | CLI flags | GenerateImage available? |
|------|-----------|----------------------------|
| Gateway chat (today) | `--print --mode=ask --trust` | **No** — read-only |
| Image job (this plan) | `--print --trust --workspace <temp>` **without** `--mode=ask` | **Yes** — `--print` documents “access to all tools, including write and shell” |

Image jobs therefore run a **narrow, prompt-bound agent turn** in an ephemeral workspace. They must **not** reuse the chat driver’s `--mode=ask` args. Do **not** pass `--force`, `--yolo`, or `--approve-mcps`.

### Mapping Gateway payload hints → bounded ratio guidance

If the Gateway sends OpenAI-style `size` (or Relay-normalized equivalents), normalize an unambiguous ratio for prompt guidance and `provider_details`; this is not a promise that Cursor receives or enforces a native tool parameter. Otherwise omit the hint and let Cursor pick its default bucket:

| Incoming hint | Requested-ratio metadata | Cursor prompt-guidance bucket |
|---------------|---------------------------|-------------------------------|
| `1024x1024`, `1:1` | `1:1` | `1:1` |
| `1024x1536` | `2:3` (the actual pixel ratio) | nearest supported portrait guidance, `9:16` |
| `9:16`, portrait | `9:16` | `9:16` |
| `1536x1024` | `3:2` (the actual pixel ratio) | nearest supported landscape guidance, `16:9` |
| `16:9`, landscape | `16:9` | `16:9` |
| `4:3`, `3:4` | same ratio string | same ratio string |
| Unknown / custom pixels | omit the ratio hint; document in `provider_details` that exact pixels are not guaranteed | omitted |

Do not reject jobs with unsupported sizes; use the closest bounded prompt guidance when useful and return whatever Cursor produced. Preserve `aspect_ratio_requested` as the actual normalized incoming ratio and, when a different bucket is used, record `aspect_ratio_guidance` separately. Never present a guidance bucket as the requested or guaranteed output ratio. Always measure and report observed dimensions when possible.

## Steps

### 1. Split chat vs image driver behavior

Use a concrete OS-authenticated bootstrap for the local status page. The Electron/tray main process requests a single-use ticket over `\\.\pipe\alorbach-ai-model-relay-status-bootstrap`, whose ACL permits only the current interactive user SID; the bridge binds the ticket hash to the current pairing generation, process/user identity, and a 60-second expiry, and never logs or persists the ticket. The main process opens `/status#bootstrap=<ticket>`; `src/status-page.js` immediately POSTs the fragment value to `/v1/status/bootstrap` with the raw loopback Origin, then clears the fragment. The server consumes the ticket atomically and sets the `HttpOnly; SameSite=Strict` status-session cookie; only then does an authenticated status `GET` receive a document ID and probe nonce. The bootstrap endpoint accepts no query-string ticket, bridge token from page JavaScript, or nonce-only substitute. Missing, expired, replayed, wrong-user, wrong-pairing-generation, or unavailable-IPC tickets leave the page read-only and make `action: "probe_capability"` return `403` without spawning. This OS-authenticated ticket is the normative mechanism for Plan 11; the existing WordPress `X-Alorbach-Bridge-Token` flow remains for paired WordPress-origin routes and is not exposed to the status page. Add bootstrap issuance, fragment clearing, wrong-user, expiry, replay, and missing-IPC tests.

Reference validation is recursive and closed-world. `input_reference_data_url` may be one canonical `data:` URL; every element of `input_reference`, `reference_images`, or `frames` may be only a canonical `data:` URL string or an object with exactly `{ "b64_json": <canonical-base64>, "mime_type": <allowlisted-image-MIME> }`. No nested object may contain `path`, `file_path`, `image_path`, `url`, `uri`, `href`, `src`, `filename`, or any other path/URL-bearing key; unknown keys, arrays/objects outside these exact shapes, non-data URLs, and more than the bounded reference count return `cursor_reference_invalid`. Reject these forms recursively before filesystem access, workspace creation, or Cursor spawn, and never reuse a generic local-file reference helper for Cursor image inputs. The native event must still report the exact materialized input set for a reference-bearing job.

The local `/v1/relay/test` handler must validate the raw request object before building any reduced provider payload. It must preserve every Plan 11 image field (`description`, `reference_images`, `input_reference`, `input_reference_data_url`, `model`, `n`, and the other allowlisted fields) for the centralized Cursor validator, and it must reject forbidden fields such as `referenced_image_paths`, `native_model`, and their aliases before refresh, workspace creation, or spawn. Dropping a field during route projection is not validation and must never turn an invalid or reference-bearing request into a different valid request.

Define status-page probe state explicitly: on the first local status-page `GET`, issue a random 128-bit `status_session_id` in an `HttpOnly; SameSite=Strict` cookie, a random 128-bit `status_document_id` in the served HTML, and a separate random 32-byte probe nonce in that document; store only hashes of all three, the current pairing generation, and expiry in the Relay process. Each document nonce record is keyed by `(pairing_generation, hash(status_session_id), hash(status_document_id))`, is echoed with both identifiers on `POST`, and has a 60-second TTL; a new `GET` rotates only that document’s nonce and never starts a probe. Key shared probe state by `(pairing_generation, hash(status_session_id))` and use the states `idle`, `probing`, `ready`, `cooldown`, and `failed`; atomically consume the document nonce before transitioning `idle`/`failed` to `probing`. Set `STATUS_PROBE_COOLDOWN_MS = 60000`: while `probing`, concurrent valid documents receive the in-flight state; while `ready` or `cooldown`, requests receive the cached state and cannot start another generation until the cooldown expires; after expiry, one request transitions to `probing` and all others observe that generation. Pairing-generation changes discard all session state. Expired, consumed, mismatched, or over-limit document records return `403`; a multi-tab request with a distinct live nonce may read the shared state but cannot bypass the one-active/one-per-cooldown rule. Add tests for nonce expiry/reuse, document-ID mismatch, four-tab behavior, pairing changes, concurrent probes, cooldown expiry, and failure recovery.

The generating probe is not enabled by a nonce or loopback Origin alone. Before serving a probe-capable status session, require the existing pairing authentication secret (or the normative OS-authenticated bootstrap ticket when that deployment has no pairing secret), bind it to the current pairing generation, and reject `GET`/`POST` probe access when that authenticated context is absent. In addition to the per-session state above, enforce `STATUS_PROBE_GLOBAL_COOLDOWN_MS = 60000`, one active probe, and at most one newly started generating probe per cooldown window across all sessions for a pairing generation, with an atomic process-wide limiter keyed by pairing generation; a new session cannot bypass it. After the cooldown expires, the next authenticated explicit probe may start one new generation; no status-page fetch starts one implicitly. Rate-limit creation of authenticated status sessions to four per pairing generation per minute and return the existing cache state during the limiter window. If pairing authentication or OS-authenticated IPC is unavailable, keep image capability hidden and never run a generating probe. The nonce remains CSRF/replay protection, not authentication.

The accepted image-selection grammar is exact: `model-relay:cursor-cli:image` is the only public Relay alias and the only provider-qualified value allowed in an incoming request or persisted `images` default; an omitted `model`, or the literal `auto`, is accepted only for a direct request that has already selected `provider: "cursor-cli"` and means “omit the native `--model` argument.” A saved/default value may not be bare `auto`, and `model-relay:cursor-cli:auto` is invalid. All other Relay aliases, native IDs, and native-model override fields return `cursor_model_invalid` before spawn. This rule removes the earlier shorthand ambiguity: missing/`auto` is a direct-provider input only, never a saved selector or generic resolver fallback.

Refactor `createCursorCliDriver` similarly to `createGrokCliDriver` / `createAntigravityCliDriver`: keep chat on `createNamedCliDriver` args (`--mode=ask`), add a dedicated `images()` implementation.

- Base `job_types` starts as `['chat']`; append `images` only after both the cached eligibility gate and a successful native GenerateImage capability probe pass.
- Keep chat available independently, but expose `images` in `driver.job_types`, `driver.supports()`, and `capabilities().job_types` only after those image gates pass.
- `capabilities().features.images`: true only when the CLI is installed, authenticated, its selected image protocol and sandbox contract are eligible, and a successful GenerateImage capability result is cached.
- `models()`: add `{ id: 'model-relay:cursor-cli:image', type: 'image', job_types: ['images'] }` only while the image gates pass; chat models stay `type: 'text'` and keep `job_types: ['chat']`.

When eligibility passes but the native capability probe has not run, expose a guarded status-page **Probe Cursor image capability** action, not the Gateway image model. That explicit user action runs the one-time probe, primes the cache on a native GenerateImage event, and never runs implicitly during refresh or a Gateway request.

Implement the probe through the local `POST /v1/relay/test` helper with an explicit `action: "probe_capability"` and `job_type: "images"`; it must call only `driver.probeImageCapability()` and must not require the hidden image model to pass normal Gateway model resolution. The probe uses a fixed bounded prompt and the same isolated protocol/workspace as a real image job, returns the cached capability state, and is available only from the local status page.

The synthetic Relay alias is an operation selector, not a Cursor-native model ID. Never pass `model-relay:cursor-cli:image` (or any other `model-relay:*` alias) to Cursor’s `--model`. This plan exposes no public native-model override: an omitted model or literal `auto` means omit `--model` only after the direct request has selected `provider: "cursor-cli"`; persisted/default routing uses the synthetic image alias or no value, never bare `auto`.

`model-relay:cursor-cli:auto` is not a second image model and must not be resolved through the generic chat model/type path. For `job_type: "images"`, branch to `resolveCursorImageModel()` before generic capability/type resolution: accept only `model-relay:cursor-cli:image` when the image gate is ready, or an omitted/literal `auto` value only when the direct request already names `provider: "cursor-cli"`; both direct forms mean omit `--model`. Reject the synthetic `cursor-cli:auto` alias, bare `auto` saved defaults, and all other aliases with `cursor_model_invalid`.

Model discovery is still an allowlist operation: the selected executable’s `models` (or verified equivalent) response is normalized to a bounded, duplicate-free set of native IDs for diagnostics and future compatibility, and arbitrary IDs or arbitrary `--model` values are never forwarded by this plan. The synthetic `model-relay:cursor-cli:image` alias is the only accepted Relay image selector; other `model-relay:*` values and explicit native-model fields fail with `cursor_model_invalid`. Missing/`auto` means omit `--model` only for a direct request that already selected `provider: "cursor-cli"`; saved image defaults may contain only the synthetic alias (or be absent), never bare `auto`. Model discovery is best-effort diagnostics only: a missing, changed, or temporarily unavailable model list must not hide an otherwise proven image capability, and its digest is not a cache-key, readiness, or attestation field under this plan. A future native-model override requires a separate provider contract and plan.

Add a dedicated `resolveCursorImageModel()` path in `src/backend-registry.js` and call it from both normal incoming-payload resolution and saved-default resolution before any image spawn. It must not reuse the existing Cursor helper’s fallback that silently converts an unknown value to `auto`: the only accepted Relay selector is `model-relay:cursor-cli:image`, and this plan deliberately forwards no native `--model` value. Foreign Relay aliases, explicit native IDs, malformed values, bare-`auto` saved defaults, and stale saved defaults return `cursor_model_invalid` with no spawn; an omitted/literal `auto` value omits `--model` only for direct requests that already selected `provider: "cursor-cli"`. Preserve this error through `relayPayloadFor()` rather than rewriting it to `backend_unsupported` or `relay_default_unavailable`.

After removing the transport envelope, validate image payloads against an explicit allowlist: `model`, `prompt`, `description`, `size`, `quality`, `image_size`, `aspect_ratio`, `resolution`, `input_reference_data_url`, `input_reference`, `reference_images`, `frames`, `n`, and `response_format`. Reject unknown keys and specifically reject `native_model`, `nativeModel`, `model_id`, `modelId`, `cursor_model`, `cursorModel`, `cursor_model_id`, `cursorModelId`, `provider_model`, `providerModel`, and `model_override` as `cursor_model_invalid` before spawning; do not silently ignore a possible native-model override.

Validate forbidden reference fields as a separate first-class branch before generic unknown-key handling: if `referenced_image_paths` or another public external-path field is present, return `cursor_reference_invalid` before creating a workspace or spawning Cursor. Only the data-URL/inline reference fields named above may proceed to materialization.

Normalize the accepted `n` field before any provider work: omit it or accept the integer value `1` only; reject `0`, negative, fractional, string, and greater-than-one values as `cursor_request_invalid` (the single-image contract does not support batching). The driver must always issue one GenerateImage turn and return one item in `response.data`.

The capability probe is a status-page mutator, not a general localhost API. Include `/v1/relay/test` in the server’s `STATUS_PAGE_MUTATORS` set for `OPTIONS`, add only `X-Relay-Status-Nonce` and `X-Relay-Status-Document` to `Access-Control-Allow-Headers`, and apply the same guard to `action: "probe_capability"` on `POST`. The `status_session_id` is transported solely in the `HttpOnly; SameSite=Strict` cookie; there is no session header. For this route/action, validate the raw `Origin` header before calling `normalizeOrigin()`: missing, `null`, malformed, non-HTTP, non-loopback, or wrong-port origins must return `403` before spawning Cursor. The Origin check is CSRF protection only, not authentication. An authenticated status-page `GET` must create a cryptographically random nonce and document ID bound to the authenticated status session and pairing generation, store only their hashes with a **60-second TTL**, and inject both one-time values into the served HTML as non-reflective `meta`/data attributes; page JavaScript sends them as `X-Relay-Status-Nonce` and `X-Relay-Status-Document` on the capability `POST`. Require the raw local Origin, authenticated pairing/OS-IPC context, cookie session, document ID, and nonce; compare secrets in constant time and atomically consume the document nonce before spawning Cursor. Missing, stale, reused, mismatched, or malformed values return `403`; a concurrent second request using the same nonce must fail. `OPTIONS` validates only the raw Origin and never spawns or consumes a nonce. The nonce and loopback Origin are explicitly not authentication or proof of page provenance; the authenticated pairing/OS-IPC context is mandatory, and if it cannot be established the mutator returns `403` and image capability remains hidden. Do not claim that only a genuine status-page process can invoke it. Rate-limit status-page GET/probe generations to one active probe and at most one newly started generating probe per cooldown window across all sessions for the pairing generation; after `STATUS_PROBE_GLOBAL_COOLDOWN_MS = 60000` expires, the next authenticated explicit probe may start one new generation. Return the existing cache state for concurrent or cooldown requests, and never start repeated expensive probes merely because a client fetched the page again. Do not treat a missing Origin as local for this mutator. Cover the preflight with the cookie plus exact nonce/document headers and both `localhost`/`127.0.0.1` status-page variants in route tests.

Route ordering must not erase the result it is about to return: branch `action: "probe_capability"` before the generic provider-test path that currently calls `statusCache.refresh()`, or use an explicit capability-preserving refresh. This branch must select the fixed `cursor-cli` driver directly from the active backend registry, without requiring a `model` field or calling normal hidden-model resolution. The guarded action must probe the current Cursor driver and return that generation’s cache state; an ordinary provider test must not clear a successful Cursor image result merely as a side effect of resolving a model. A true refresh/rebuild may invalidate the result, but it must do so before a new capability probe and before any image model is resolved. The handler must return the state from the same cache generation captured before spawning.

### 2. Probe and cache CLI contract on `refresh()`

Cursor identity is a separate trust gate: the selected executable, every bootstrap target, and the final process image must all pass Windows `WinVerifyTrust` against the pinned Cursor publisher/certificate chain, must be inside the signed allowlisted Cursor installation roots with matching product metadata, and must have a non-writable ancestor chain. Installation-root allowlisting is an additional condition, never an alternative to signature verification; version, help, model output, and a familiar executable name are not product identity proof. Bind the verified publisher thumbprint/chain, installation-root identity, realpaths, and digests into the stable capability snapshot and every per-job launch attestation; any missing, unknown, unsigned, or mismatched identity fails the image gate as `cursor_cli_unsupported` while leaving chat available.

The image baseline accepts only a directly resolved, signed `.exe` bootstrap. A `.cmd` chain is unsupported unless the native helper resolves the complete chain before launch and creates the final verified executable with the child-process restriction applied as a process-creation attribute before its first instruction; applying the restriction after the shim or final process starts is not sufficient. The resolver must therefore return `cursor_cli_unsupported` for `.cmd` image launches when that pre-dispatch guarantee is unavailable, while preserving any existing `.cmd` behavior for chat.

During refresh, resolve exactly one Cursor CLI executable and argv prefix before running any non-generating eligibility preflight. Use one shared `resolveCursorExecutable()` result for version, authentication, model discovery, capability flags, ACP, print mode, and the host-security smoke. Candidate order is configured command, `AI_MODEL_RELAY_CURSOR_BINARY`, and the legacy `cursor-agent` command. Consider the generic `agent` command only when it is explicitly configured or its product signature/help/version contract positively identifies Cursor Agent; never treat an unrelated bundled `agent` executable as a Cursor candidate. Deduplicate candidates resolving to the same verified realpath and reject ambiguity only among distinct, positively verified Cursor executables. On Windows resolve the actual `.exe`/`.cmd` target and its command-shim target, and use that same resolved executable/argv shape for every subsequent probe. A `.ps1`-only shim is unsupported for image mode in Plan 11; chat may retain existing PowerShell behavior, but image eligibility must return `cursor_cli_unsupported` unless a future compatibility plan resolves and hashes the complete PowerShell script, Node runtime, entrypoint, and argument tuple. Do not hard-code a different executable name in individual drivers. The official `agent acp` invocation is eligible only after that product verification; a legacy `cursor-agent acp` invocation is eligible only when the same resolver verifies all required commands against that binary. This preflight must not advertise image readiness by itself:

- `<resolved-cursor-executable> --version` and parse either stable SemVer (`major.minor.patch`, optional build metadata but no prerelease) or Cursor’s date-build format (`YYYY.MM.DD[-build]`, including the observed `2026.08.31-4057e58`). Match the complete version output after an optional known product label; require exactly one accepted token, reject mixed/multiple candidates, reject leading-zero SemVer components, and validate the date with calendar rules. Accept SemVer `>= 2.4.0` or valid date-builds on/after the documented 2.4 release date **2026-01-22**; reject unknown, ambiguous, prerelease, malformed, and pre-feature formats. Keep the raw version and normalized comparison kind in diagnostics.
- Use `<resolved-cursor-executable> status` and `<resolved-cursor-executable> models` (or the one verified equivalent argv for that executable) for authentication and model discovery; never run those probes through another candidate after selection.
- For print protocol: `--print` and `--output-format stream-json` support (required); plain `--output-format json` is not sufficient because it omits the event stream. Before marking this protocol eligible, run `<resolved> --help` and relevant subcommand help, then run a harmless disposable-workspace fixture proving any selected `--workspace` flag is accepted and actually becomes the working root. `--workspace`, `--trust`, and `--sandbox enabled` are optional compatibility flags: append each only when the exact help output and harmless fixture for that installed build prove it is supported and has the intended behavior. Native helper enforcement remains mandatory even when a flag is accepted; an unsupported flag does not permit a direct spawn. Verify the required noninteractive behavior; if `--trust` is unsupported, ignored, or prompt suppression is unverified, do not pass it and keep print mode unsupported.
- For ACP protocol: `acp` stdio subcommand, JSON-RPC session flow, `clientCapabilities`, an explicitly negotiated and acknowledged full `agent` mode, permission rejection, and `cursor/generate_image` notification support (required). `--sandbox enabled` is an optional compatibility flag and may be appended only after exact help/fixture confirmation; the native helper remains mandatory regardless.
- Optional: whether `--mode` accepts only `plan`/`ask` (confirms image jobs must omit `--mode=ask`)
- A successful project-scoped permission/sandbox configuration probe using the exact generated files and flags described in Step 4; verify that denied shell, web, MCP, out-of-workspace file actions, and temporary-directory writes are rejected without an approval prompt. The probe may also normalize a bounded list of exact native IDs for diagnostics, rejecting duplicate/invalid IDs, but model-list failure or digest changes must not affect image readiness, the cache key, or the attestation. This plan forwards no explicit native model; `auto`/missing omits `--model`, and every other `model-relay:*` value or native-model field is rejected as `cursor_model_invalid`.

On Windows, the Cursor flags and profile files are only advisory inputs to the named `native/cursor-image-sandbox/cursor-image-sandbox.exe`; they are never the sole security boundary. That helper must launch the resolved Cursor process under a restricted/AppContainer token, an ACL-scoped workspace, and a Job Object with both `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and an active-process limit that prevents any unauthorized child task from being created. Its DACL must grant read-only access to the workspace root, sealed `workspace/input`, auth projection, verified executable/shim/runtime/system roots, and OS trust/keychain interfaces; grant modify access only to `workspace/assets` and the explicitly enumerated disposable per-job profile scratch roots; and deny write/create/delete/rename for `prompt.txt`, `.cursor/`, and every other workspace path. The only permitted bootstrap is the exact resolver-attested native executable and command-shim target; a `.ps1`-only shim is rejected for image mode, and any other child creation, including a Cursor subagent, must be rejected before dispatch. It must install an ephemeral per-job Windows Filtering Platform boundary (or route all child traffic through a Relay-owned allowlisting proxy) that permits only the verified Cursor provider-control-plane endpoints and the proxy loopback, while denying direct arbitrary egress, browser/WebFetch, and MCP traffic. The helper owns the CreateFileW handle-based artifact read described in Step 5, returns process/network/filesystem evidence, and returns that evidence to the Relay.

The native helper ABI is `cursor-image-sandbox/v1`: one length-bounded canonical UTF-8 request and one length-bounded canonical UTF-8 response over a private stdio pipe; the exact encoding and field contract are defined by the packaged and signed `attestation-abi-v1.md`. For every launch, the Relay generates a fresh 32-byte cryptographically random `challenge_nonce` and 128-bit `job_id`; neither may be reused. The request contains `abi`, nonce, job ID, helper path/digest, Cursor executable and shim realpaths/digests, explicitly enumerated read-only runtime/system roots, bounded writable scratch/profile roots, workspace/auth-projection/process-temp identities, policy and config hashes, requested protocol/mode, and expiration. The helper response contains the same nonce/job ID and ABI plus child PID, Job Object identity, helper identity, ACL-policy hash, WFP/proxy-policy hash, endpoint-policy ID/hash, process-child-limit state, workspace/auth/runtime/scratch identities, monotonic start/finish times, and only claims backed by its OS probes. `src/security-attestation.js` implements the signed ABI contract, uses RFC 8785 JSON Canonicalization Scheme (JCS) over UTF-8, rejects duplicate keys, non-finite numbers, invalid Unicode, and non-canonical encodings, and verifies the ABI, exact nonce/job ID, single-use/expiration, signed helper/policy/config manifest and Authenticode identity, path/digest fields, child PID ownership by the Job Object, ACL/WFP probes, and all expected policy values; missing, extra, replayed, stale, unproven, or mismatched fields reject the launch. The helper cannot self-authorize: its response is evidence only. After independent verification, the Relay may sign an in-memory attestation with an ephemeral per-process key held only in memory; it never persists the key or a consumable attestation. `trust-anchor.json` pins the release-manifest public key and publisher thumbprint, while a process restart always resets readiness and requires a fresh challenge. Any serialized attestation copy is diagnostic only and must be rejected after restart or process-generation change. `scripts/build-cursor-image-sandbox.js` must build this helper with the project’s MSVC toolchain, place the architecture-specific binary at the exact `native/cursor-image-sandbox/bin/win32-x64/cursor-image-sandbox.exe` packaging path, update `build.extraResources` to include that binary, `trust-anchor.json`, `manifest.json`, `manifest.sig`, `attestation-abi-v1.md`, `cursor-auth-profile.compat.json`, `network-policy.compat.json`, `cursor-cli-config.compat.json`, and `cursor-sandbox.compat.json` at stable `native/cursor-image-sandbox/` resource paths, verify its exported launcher/reader ABI and SHA-256 digest, generate the canonical policy/config/resource digests and release manifest before Electron Builder runs, and fail when the helper, ABI document, policy/config resources, or attestation ABI is absent. The release job must provide the protected Authenticode PFX/password to `signtool.exe`, sign the helper with SHA-256, generate `manifest.json` containing the exact helper/policy/config/ABI-document paths, canonical bytes and SHA-256 digests, build ID, and ABI, and sign it with the protected manifest key whose public key is checked into `trust-anchor.json`; if any signing input or verification tool is unavailable, fail before producing release artifacts. `native/cursor-image-sandbox/trust-anchor.json` must pin the helper’s ABI and expected Authenticode publisher certificate thumbprint plus the release-manifest public key; `src/native-helper-integrity.js` must resolve these resources from `process.resourcesPath` in packaged mode (and the repository native-resource root in development), call Windows `WinVerifyTrust`, validate the pinned publisher and manifest signature, canonicalize and verify the listed auth/network/config policy and ABI-document bytes and digests, and reject any digest/path/ABI/policy/config mismatch before every capability probe and every image job. The helper’s realpath and digest must be included in the cache key and attestation, and the packaged smoke must assert all nine resources are present, invoke that exact binary, exercise the handle reader during a replacement race, and verify that the child-creation and egress denials occur before execution. A non-Windows implementation must provide equivalent pre-dispatch child denial, no-follow reads, and egress enforcement; otherwise image capability remains disabled on that platform.

The packaging contract is exact: `build.extraResources` must contain entries mapping `native/cursor-image-sandbox/bin/win32-x64/cursor-image-sandbox.exe`, `native/cursor-image-sandbox/trust-anchor.json`, `native/cursor-image-sandbox/manifest.json`, `native/cursor-image-sandbox/manifest.sig`, `native/cursor-image-sandbox/attestation-abi-v1.md`, `native/cursor-image-sandbox/cursor-auth-profile.compat.json`, `native/cursor-image-sandbox/network-policy.compat.json`, `native/cursor-image-sandbox/cursor-cli-config.compat.json`, and `native/cursor-image-sandbox/cursor-sandbox.compat.json` to the same relative paths below the packaged resources root. `src/native-helper-integrity.js` must resolve those nine paths from `process.resourcesPath/native/cursor-image-sandbox/` when packaged, assert that all exist and are regular files, canonicalize the policy/config/ABI bytes, and verify the signed manifest path/digest for every resource before launch. A missing resource, path substitution, unsigned policy/config/ABI document, or generated-manifest mismatch fails the build and keeps image capability hidden.

The runtime filesystem matrix is normative and is included in the helper request, policy hash, and attestation: grant read-only access to the verified Cursor executable, command shim, their containing installation/runtime directories, the minimal Windows system/runtime directories needed to load signed DLLs, and OS certificate/keychain APIs or their documented read-only backing stores; grant read-only access to the sealed auth projection and materialized `workspace/input`; grant bounded create/modify access only to the disposable per-job profile scratch roots and `workspace/assets`; and deny all access outside these enumerated roots. The fresh profile roots are not the user’s global profile and are deleted only after descendant exit. The artifact-workspace shorthand above is therefore scoped to that workspace: `input/` is read-only after materialization, `assets/` is the only writable workspace subtree, and `prompt.txt`, `.cursor/`, and all other workspace paths remain non-writable. If a Cursor build needs a runtime path or write outside this matrix, its compatibility fixture must enumerate and verify that exception or the image capability remains disabled.

The `.cursor/cli.json`, `.cursor/sandbox.json`, and optional `prompt.txt` files are the sole pre-sealing exception to the workspace write deny: create the config files from the signed compatibility resources and create `prompt.txt` only for the bounded `@` convenience mention, canonicalize/hash all materialized bytes, verify their schemas/limits, and only then apply the helper’s read-only ACL to `.cursor/` and `prompt.txt`. No Cursor process runs between materialization and sealing.

The documented CLI does not expose a separate entitlement-only query. Therefore the eligibility preflight must leave image readiness `unknown` until the explicit status-page probe receives the selected protocol’s native `GenerateImage` event with a generated artifact. A native tool rejection, missing tool event, or “image generation unavailable” response invalidates the cached image capability and returns `cursor_cli_unsupported` without fallback. Gateway jobs must not silently generate a probe image.

Store protocol, negotiated full-Agent mode, flags, normalized version, resolved executable realpath, a SHA-256 digest of the executable and command-shim target, the packaged native-helper realpath/digest/ABI, isolation, Cursor-specific authentication generation, and capability result on the cached snapshot. An explicit Cursor auth-profile logout, re-authentication, account change, auth-generation change, auth revalidation failure, and backend rebuilds clear the native capability result to `unknown`; a browser/WordPress status-page pair or unpair does not change Cursor auth generation. A cached success is reusable only when the executable/helper realpaths and digests, normalized version, protocol/mode, canonical contents of the sandbox/permission/profile contract, and opaque Cursor auth generation are unchanged. If the executable/helper cannot be hashed or its digest changes while the reported version remains the same, invalidate and re-probe. The reusable cache key must not contain a per-request temp workspace or profile root: those paths are intentionally fresh for every job. Materialize and validate each fresh profile against the same canonical contract before spawning, and invalidate when the contract or its effective isolation behavior changes. The model-list digest is diagnostic only and is not a cache-key, readiness, or attestation field under this plan. Deduplicate concurrent probes for the same cache key and discard an in-flight result if that key changes. Do not infer image readiness from generic authentication, `--print` success, or prompt text alone. A failed image gate removes `images` from dynamic job types and hides the image model while preserving chat.

Define the opaque Cursor auth generation instead of assuming one exists: `src/local-cli.js` and the dedicated Cursor auth-profile lifecycle own a monotonic in-memory or persisted generation that increments on that profile’s login, logout, re-authentication, account change, or any Cursor authentication-status transition. A non-generative Cursor auth/status check may additionally return a documented account identifier; hash only that identifier into the cache key and never store credentials or raw account output. The supported handoff is the operator-run `agent login` flow with `CURSOR_CONFIG_DIR` set to the dedicated Relay auth profile; Gateway jobs never perform interactive login and never receive an API key/token. Browser/WordPress status-page pairing is a separate CSRF/session lifecycle and must not increment or substitute for Cursor auth generation. If the installed CLI exposes no stable non-secret account identity, do not reuse image readiness across a bridge restart, explicit refresh, or Cursor auth/status check; mark it `unknown` and require the guarded capability probe again. An auth failure or changed account identity invalidates readiness before models/capabilities are advertised. If a stable identity and unchanged Cursor auth generation are available, ordinary provider tests may preserve a successful image capability; if either is unavailable, every Cursor auth/status check invalidates native image readiness and any such ordinary test must re-run the guarded capability probe before image resolution. The explicit `action: "probe_capability"` path is separate and never performs that generic refresh.

Authentication projection is a version-pinned compatibility gate, not an invented file copy. `test/fixtures/cursor-auth-profile.compat.json` must record for each supported Cursor build the exact `CURSOR_CONFIG_DIR` routing behavior, relative persisted auth-file manifest and formats, keychain/service dependencies, required ACLs, projection copy rules, and a non-generative login/status verification transcript. The implementation may project only that recorded file set and must prove the projection authenticates the pinned build without API-key/token environment variables. Because the public Cursor authentication documentation does not define this file set or routing variable, absence of a matching compatibility fixture explicitly defers image readiness for that build; do not guess filenames, keychain behavior, or profile semantics.

Make refresh generation-aware: `src/status-cache.js` and the backend rebuild path must increment a generation before replacing drivers, capture that generation/key in each non-generating preflight, and publish results only when both still match at completion. A refresh already in progress must not mark a newly rebuilt driver ready. Changed executable realpath/digest, version, protocol, canonical sandbox/profile contract, permission/resource-policy hash, or opaque auth generation invalidates the cached image result to `unknown` and schedules at most one shared non-generating eligibility refresh; it must never start `GenerateImage`. Only the explicit guarded `action: "probe_capability"` status request may start the one-time generating capability probe, and it must capture the current generation/key before spawning. If a completed in-flight preflight or capability result no longer matches the current generation/key, discard it, clear the old in-flight marker, and leave the cache `unknown` (or allow the one explicit caller to retry); never enqueue a generating follow-up from refresh and never leave the cache permanently `checking`. A changed per-job temp root alone must not invalidate a reusable capability result, but failure to materialize or validate the new isolated root must fail closed for that job. Auth revalidation must be non-generative and must not silently run an image probe.

Keep two gates separate: the reusable cache proves only stable CLI/protocol/auth eligibility and the canonical isolation contract; it never authorizes a job by itself. Every image request must create its fresh disposable profile, materialize the canonical permission/sandbox files, and produce per-job isolation evidence (profile roots, file hashes, effective deny-test results, and explicit child environment) before spawning Cursor. Require that evidence to match the cached contract and current generation; if the fresh profile is unvalidated, reuse of the capability cache must not bypass the job gate.

Pass a `securityAttestation` only when the Relay’s own in-process/orchestrated smoke probe produced it from a fresh cryptographic challenge. It must bind the attestation to the resolved Cursor executable and command-shim realpaths/digests, the packaged native-helper realpath/digest and ABI, normalized version, selected protocol, negotiated full-Agent mode, exact argv, Cursor-specific auth generation/account-identity hash, policy/profile/sandbox hashes, provider-control-plane endpoint allowlist, host/OS, process generation, and an expiration timestamp. `ready` is consumable only when the attestation is present, unexpired, and every field equals the current snapshot; a missing, stale, mismatched, externally edited, or untrusted JSON record yields `unknown`. Do not persist a consumable attestation or its signing key: an ephemeral per-process key may protect the in-memory value, but any serialized copy is diagnostic only and is rejected after restart or process-generation change. CI fixtures may supply a declared fixture attestation for mock tests, but a real installed image capability cannot be exposed without a live matching attestation. Revalidate the signed helper/policy manifest, helper digest, and policy bytes immediately before every image job, not only during refresh.

Use two explicitly separate attestation layers. The stable capability attestation covers only installation/protocol/auth/configuration facts and proves that the explicit status probe succeeded; it is the value cached for readiness and never contains a per-job workspace, profile, prompt, nonce, or job ID. Each image request then obtains a fresh per-job launch attestation after the helper has materialized the job roots, sealed config/input/prompt files, resolved the endpoint policy, and returned the OS evidence. That launch attestation binds the fresh paths, file identities/hashes, sanitized environment, concrete argv, helper challenge, process generation, and job ID, is consumed once by that job, and is never reused as a capability cache entry. A fresh per-job attestation is mandatory even when the stable capability attestation is still ready.

The helper must make executable launch race-safe: before creating the process, open handles for the resolved executable, command shim/target, and every allowlisted runtime directory or file with write/delete sharing denied where Windows permits; record volume/file-index, size, timestamps, and SHA-256 identities; and keep the handles until process creation and the first process-image check complete. Use the same canonical paths and argv that were verified, and immediately open the actual process image with a no-follow handle to verify its publisher, realpath, volume/file-index, and digest against the attested tuple before any protocol message or network request is allowed. If the platform cannot launch from a verified handle, the held no-delete handles plus the immediate process-image identity check are mandatory; any replacement, identity mismatch, or unverified bootstrap terminates the tree and returns `cursor_cli_unsupported`. The helper ABI and smoke must record this pre-launch and post-launch identity evidence, including the accepted `.exe`/`.cmd` bootstrap chain.

The same race protocol applies to the packaged helper itself: the Relay opens the exact helper binary from the verified packaged resource root with no-follow and write/delete sharing denied, checks its Authenticode publisher, path, volume/file-index, SHA-256, and ABI before launch, holds the resource handle through helper process creation, and opens the actual helper process image to repeat the identity check before accepting one byte of helper evidence. The fresh challenge binds that helper identity, ABI, and process generation; any helper replacement or mismatch kills the helper and Cursor tree and returns `cursor_cli_unsupported`.

Child creation is a separate pre-dispatch gate: after the accepted `.exe`/`.cmd` bootstrap reaches the final Cursor process, the helper must apply Windows `ProcessChildProcessPolicy` with `NoChildProcessCreation` (or the documented `PROCESS_CREATION_CHILD_PROCESS_RESTRICTED` equivalent) to that actual process, deny job breakaway (`JOB_OBJECT_LIMIT_BREAKAWAY_OK` is never enabled), and retain the Job Object active-process limit as a second boundary. The bootstrap exception is narrowly limited to the resolver-attested command-shim target and must end before ACP/print protocol messages are accepted. The probe launches a harmless child-attempt fixture from the final process and requires `CreateProcess` to fail before the child has any file/network side effect; an unavailable mitigation API, breakaway path, or ambiguous bootstrap chain keeps image capability disabled.

### 4. Run cursor-agent for one GenerateImage turn

Provider permission configuration must use only documented Cursor permission keys and exact observed values from the signed, version-pinned `cursor-cli-config.compat.json` compatibility fixture; the documented baseline is limited to the supported Shell/Read/Write scopes. `WebFetch(*)`, `Mcp(*:*)`, browser, and subagent labels in the enforcement matrix are test/control requirements, not permission-file keys: they must be enforced by the native helper, the Relay-owned proxy, and the pre-dispatch child policy. ### Image security boundary

Print mode has no inherent pre-dispatch one-call guarantee. It is eligible only when the Relay-owned provider egress proxy/interceptor can recognize the verified Cursor GenerateImage operation, bind its request/tool identity to the job ID, allow exactly one request, and reject a second request before it reaches the provider. A stream-json parser, native event count, or post-launch duplicate check is not sufficient. Until that interceptor is implemented and exercised, keep print mode unsupported and use ACP only when ACP independently satisfies the same one-call gate.

The one-call budget is a precondition, not a post-parse observation. Before the first image prompt, the selected protocol and native helper/proxy must establish an enforceable per-job budget of at most one native GenerateImage dispatch, tied to the job ID and the verified protocol/tool request or provider operation identifier. For ACP, the documented fire-and-forget notification is acceptable only when the captured versioned contract or the outer provider proxy proves that a second GenerateImage dispatch is rejected before the provider request starts; otherwise ACP image capability remains unsupported. A duplicate notification remains an anomaly and must fail the job, but parser rejection after the first side effect is not a cost or safety control.

Cursor image mode intentionally omits `--mode=ask`, so the CLI has write/tool access. Prompt prohibitions are advisory only and do not isolate the image tool. Do not advertise or execute `model-relay:cursor-cli:image` unless the selected execution path provides a machine-enforced permission, sandbox, or tool restriction that prevents shell, browser, MCP, subagent, and unrelated file operations, the subagent restriction is enforced before dispatch, global Cursor policy cannot widen the disposable profile, and the child process runs without Relay/API credentials in its inherited environment.

The temporary workspace limits generated-file exposure and is deleted in `finally`, but it does not by itself provide provider-side isolation. If neither the verified print-mode contract nor the ACP path plus the native OS boundary can provide the required enforceable boundary, keep the image capability disabled and return `cursor_cli_unsupported`; ACP permission handling is part of the verified protocol path above, not permission to weaken this gate.

### 5. Collect and validate the artifact

The decoder worker has its own documented `decoderWorkerEnvironment-v1` allowlist in the signed `attestation-abi-v1.md`, separate from the Cursor child allowlist. Its only permitted keys are `ELECTRON_RUN_AS_NODE=1`, `ELECTRON_NO_ATTACH_CONSOLE=1`, the verified `SystemRoot`/`WINDIR` loader value, and the job’s sibling process-temp `TEMP`/`TMP` values; the canonical key/value-template bytes are hashed in the release manifest and the concrete per-job values are hashed in the helper request and launch attestation. `PATH`, `NODE_PATH`, `NODE_OPTIONS`, Relay/provider credentials, and every other inherited variable are absent. The worker must reject any missing, extra, or mismatched environment value before loading `sharp`, and the packaged smoke must assert the exact environment hash.

The packaged decoder launch is fixed and does not use ambient module resolution: `scripts/build-win.js` must place `src/image-decode-worker.js` at `resources/app.asar.unpacked/src/image-decode-worker.js`, unpack the pinned production `sharp` package plus its architecture-matched `@img/*` native modules under `resources/app.asar.unpacked/node_modules/`, and include the worker, `resources/app.asar`, every unpacked decoder file, and their canonical SHA-256 digests in the Authenticode-signed NSIS installed-resource set and release manifest. The parent must launch the worker only through the native helper’s decoder-launch operation using the signed Electron `process.execPath`, `ELECTRON_RUN_AS_NODE=1`, the absolute unpacked worker path, a fixed resources-root cwd, and an explicit non-credential environment; it must pass the worker into the helper Job Object before the first instruction and load `sharp` by the verified absolute packaged path. Any asar/unpacked path, native-module ABI, digest, executable, or helper-launch mismatch disables image capability. Packaged smoke must inspect these exact paths, verify the signed manifest and installed-resource hashes/ACLs, decode the PNG/JPEG/WebP fixtures through this launch path, and prove timeout, memory, process-temp, and no-child enforcement.

Artifact identity must also exclude NTFS/POSIX hardlink escapes. The provider-created output must be a fresh file created for this job through a helper-owned exclusive-create handle, or the helper must prove that the native event path names a file first created/modified by this job; on Windows require `BY_HANDLE_FILE_INFORMATION.nNumberOfLinks == 1` and on POSIX require `st_nlink == 1` before and after the no-follow read. Record that link count with the file identity and reject any link-count change, hardlink to an external file, or pre-existing multi-link artifact as `cursor_image_artifact_invalid`; add Windows and POSIX hardlink-to-outside-workspace tests. Path containment, reparse/symlink rejection, and final-handle identity checks are necessary but do not replace this link-count gate.

If decoder limits require a worker or subprocess, that decoder is part of the same signed sandbox contract. The packaged Relay resource root and the exact production `sharp` JavaScript/native module files used by the worker must be enumerated by canonical path and SHA-256 in the signed manifest, included as read-only roots in the helper request and attestation, and opened from `process.resourcesPath` rather than from workspace, profile, or ambient module search paths. Launch the worker under the same no-child/bounded-process, CPU deadline, memory limit, and process-temp policy; a missing digest, unverified module, or inability to prove those limits keeps image capability disabled. The worker may read only the candidate artifact through the helper’s no-follow handle path and may write only Relay-owned result memory, never workspace files.

Resolution order (only after exactly one native GenerateImage event has been observed):

1. Parse the selected protocol’s native GenerateImage event. For print mode, require the verified `stream-json` tool event; for ACP, require the documented `cursor/generate_image` notification and its `toolCallId`. The notification is not a completion response: continue reading until the matching `session/prompt` JSON-RPC result reports a terminal `stopReason` or an explicit failure, while retaining the notification’s candidate path/data. Reject zero or multiple native image events, and treat rejected/cancelled outcomes or a terminal result without a generated event as failure.
2. Parse the event’s artifact path. The native event must identify the sole candidate with an exact path and `toolCallId` correlation; if the selected protocol can report a stable artifact identity keyed to that tool call, verify that identity as well. A textual `IMAGE_PATH:` marker from stdout/stderr/JSON text (reuse `findImagePathMarker` / validation helpers; generalize or duplicate from Antigravity with `cursor-cli` error codes) is additive only: it may cross-check the exact native path but can never locate or replace it. Do not scan `assets/` or select the newest changed file. Require the event path to be newly created or modified by this job, outside `input/`, and attributable to the native event; an old or unchanged file never qualifies. Apply explicit decoder/resource limits to both references and outputs before allocation: `MAX_COMPRESSED_BYTES = 20 MiB`, `MAX_IMAGE_DIMENSION = 8192`, `MAX_IMAGE_PIXELS = 16,777,216`, `MAX_IMAGE_FRAMES = 1`, `MAX_DECODE_TIME_MS = 5000`, and `MAX_DECODE_MEMORY_BYTES = 64 MiB`. Reject APNG, animated WebP, multi-frame images, dimensions above either bound, decompression bombs, and decoder work that exceeds the time or memory budget. The decoder must enforce limits before allocating pixel buffers; if `sharp` cannot enforce a CPU/memory bound, run it in an isolated worker/process with those limits and fail closed on timeout or overrun. Reject every symlink or reparse point for an artifact, even when its resolved target remains inside the workspace; additionally require the resolved path to be outside the entire `input/` tree. Read the exact event path before import and require strict PNG/JPEG/WebP magic-byte validation, extension/MIME consistency, regular-file status, size ≤ `MAX_COMPRESSED_BYTES`, workspace realpath containment, and full structural decode validation. If ACP supplies inline `imageData` or any undocumented outcome field, reject the message as `cursor_cli_unsupported` rather than guessing its encoding or wire location.
3. If a valid native GenerateImage event has no artifact path, return `cursor_image_artifact_missing` only after that single event and a completed terminal run. A marker-only line, an event without `toolCallId` correlation, a path mismatch, or a directory scan never qualifies; without a valid native event, return `cursor_cli_unsupported`.

Validate imported path with `pathIsInside(workspace, path)` only (not the user’s real project tree). Implement this through named `readValidatedImageArtifact()` and `validateImageBytes()` helpers in `src/image-validation.js`, backed by the pinned `sharp` full decoder for PNG/JPEG/WebP. Reject symlinks and reparse points before resolving them, require the resolved path to be outside the complete `input/` tree, and open/read the artifact through a no-follow handle. On POSIX, anchor an `openat` walk at a workspace directory descriptor and use `O_NOFOLLOW` for the target and each component where available. On Windows, delegate the read to `native/cursor-image-sandbox/cursor-image-sandbox.exe`: open every parent and the target through `CreateFileW` with `FILE_FLAG_OPEN_REPARSE_POINT` and suitable read/share/open-existing flags; reject `FILE_ATTRIBUTE_REPARSE_POINT` on every parent and the target, obtain the final path with `GetFinalPathNameByHandleW` plus volume-serial/file-index identity from `GetFileInformationByHandle`, verify containment and input exclusion, and return bytes read from that stable handle. Compare handle identity, size, and modification state before and after the read; never fall back to `readFileSync(path)`. If the native helper/primitive is unavailable, fail closed. The full decoder must reject truncated or structurally malformed PNG/JPEG/WebP data (dimensions-only inspection is insufficient), enforce all stated pixel/frame/time/memory limits, and return exactly **one** image in `response.data`.

The decoder dependency is not optional: add a pinned, non-range `sharp` version under production `dependencies` (never only `devDependencies`) in `package.json` and `package-lock.json`, selected against the project’s Electron target (currently Electron 42), while build tooling remains in `devDependencies`. `scripts/build-win.js` must assert that `dependencies.sharp` is present and that the packaged production dependency is included, invoke `scripts/build-cursor-image-sandbox.js`, run the project’s Electron-compatible native rebuild (`npx electron-builder install-app-deps` or the checked-in equivalent) during Windows packaging, and fail the build if the packaged runtime cannot load that exact decoder or the architecture-matched native helper. Add `test/packaged-image-validation.test.js` to load `sharp` and `native/cursor-image-sandbox/bin/win32-x64/cursor-image-sandbox.exe` from the packaged/unpacked Electron app at an explicit app path, decode one PNG, JPEG, and WebP fixture under the same limits, and exercise the handle reader, process-child denial, and egress boundary. Expose a stable transport contract for every Cursor-specific failure: the JSON error body contains exactly safe `error.code`, `error.category`, and boolean `error.retryable` fields, and the server maps them without collapsing them into a generic resolver error. Use `cursor_reference_invalid` → HTTP **400**, category `validation`, retryable `false`; `cursor_request_invalid` → **400**, `validation`, `false`; `cursor_model_invalid` → **400**, `validation`, `false`; `cursor_cli_unavailable` → **503**, category `unavailable`, `true`; `cursor_cli_unsupported` → **503**, category `unsupported`, `false` until configuration/upgrade changes; `cursor_rate_limited` → **429**, category `rate_limit`, `true` (include only a safe provider-derived `Retry-After` when validated); `cursor_image_artifact_missing` → **502**, category `provider_error`, `true`; `cursor_image_artifact_invalid` → **502**, category `provider_error`, `false`; and `cursor_timeout` → **504**, category `timeout`, `true`. Apply the same mapping to local `/v1/relay/test` and signed Gateway responses, test exact status/body pairs, and preserve these codes for explicit selections and saved defaults.

Implement `publicRelayError()` in `src/error-projection.js` and call it from both local and signed server error paths before serialization/signing. Its public object may contain only `{ code, category, retryable, message }`, where `message` is a static safe message selected by code. Strip `details`, raw stdout/stderr, prompt text, file paths, workspace/profile paths, executable/helper paths and digests, endpoint lists, auth/account identifiers, security attestations, nonce values, and arbitrary provider payloads. A protected local diagnostic log may retain a redacted correlation ID and internal evidence, but that record must never be copied into the response or signed Gateway payload. Tests must assert that each mapped error contains no details or sensitive path/hash/endpoint/attestation material.

In `src/server.js`, implement `errorStatusForResult()` for this mapping and use it in both the local `/v1/relay/test` resolver-error branch and the signed `/v1/relay/jobs/images` resolver-error branch. Preserve the existing top-level compatibility fields (`code`, `category`, and safe `message`) while adding/returning the nested `error.code`, `error.category`, and `error.retryable` contract; do not let the existing catch-all 503 branch override a validated 400/429/502/504 Cursor result.

Apply failure precedence deterministically: (1) validate request references and return `cursor_reference_invalid` before spawning; (2) validate the image selector and return `cursor_model_invalid` before spawning; (3) return `cursor_cli_unavailable` only for missing/unspawnable executable or failed non-generative authentication; (4) after the selected executable/protocol is established, classify a **structured provider** rate-limit response as `cursor_rate_limited` even when it arrives before a native GenerateImage event; accepted evidence is only a protocol error/status event with a provider rate-limit code/status (`429`, `rate_limit`, or `too_many_requests`) and optional validated `Retry-After`, never arbitrary prompt/output text; (5) return `cursor_cli_unsupported` for every available-but-unknown/failed version, protocol, capability, transport, auth-generation, profile, sandbox, permission, or native-event gate; (6) classify a completed native run with no candidate as `cursor_image_artifact_missing`, and a candidate that fails structural, freshness, MIME, size, symlink, or containment validation as `cursor_image_artifact_invalid`. Explicit and saved Cursor image selections must preserve these Cursor-specific codes and never rewrite them to generic resolver errors; chat errors remain on the existing chat path.

When an explicit `model-relay:cursor-cli:image` selection or the saved `images` default targets a Cursor driver whose image gate is unknown/failed, the resolver must return `cursor_cli_unsupported` with the selected model and safe diagnostic. `relayPayloadFor()` must recognize the provider from the saved default as well as from the incoming payload and preserve this Cursor-specific code for defaults; do not collapse the explicit error into `backend_unsupported`, and do not rewrite the saved-default error to `relay_default_unavailable`. That code tells the caller the selected Cursor capability is not currently supported. Chat resolution must remain unaffected.

### 6. Normalized response

Public job/status snapshots are a separate projection boundary from internal runner diagnostics. Cursor session output, stdout/stderr, prompts, paths, hashes, endpoint data, auth identifiers, and attestations must be suppressed or redacted before JobManager stores status events and before `/v1/status` serializes a snapshot; retain such evidence only in a protected local diagnostic record that is never returned or signed. Tests must create a failed Cursor job and assert that its status snapshot contains only the documented safe job state and projected error fields, with no raw output or sensitive diagnostic material.

Error classification is determined by root cause and is independent of the caller or selector source: a missing or unspawnable executable, or a failed non-generative authentication check, is `cursor_cli_unavailable`; an installed and authenticated executable whose version, protocol, capability, policy, profile, isolation, attestation, or native-event gate is unknown or failed is `cursor_cli_unsupported`. Explicit selections and saved defaults must preserve that same cause-based result, so resolver context never reclassifies an unavailable installation as unsupported or an available-but-incompatible installation as unavailable.

Return:

```json
{
  "success": true,
  "response": {
    "data": [{ "b64_json": "...", "mime_type": "image/png" }],
    "provider_details": {
      "provider": "cursor-cli",
      "tool": "GenerateImage",
      "aspect_ratio_requested": "1:1",
      "aspect_ratio_guidance": "1:1",
      "artifact_imported": true,
      "reference_images": 0
    }
  }
}
```

Include observed width/height in `provider_details` after structural decode when cheap (`readImageDimensions` already exists for job artifacts); dimensions are metadata, never an artifact-integrity gate by themselves.

### 7. Concurrency

The “do not change `job-manager.js`” default below is limited to concurrency locking and does not prohibit the required security projection. Cursor runners must not send raw session output to `appendSessionOutput`; either add a provider-aware redacting storage path in JobManager or return only safe Cursor status fields and keep raw evidence in a protected diagnostic sink. The redaction must cover `/v1/status`, SSE, and IPC snapshots as well as HTTP error bodies, with tests for each surface.

Per-job `--workspace` + `assets/` should **not** need Codex’s global `generated_images` lock. Do **not** change `job-manager.js` unless tests prove two concurrent Cursor image jobs can import the same file; if they can, rely on existing per-provider image concurrency (`provider:cursor-cli`).
